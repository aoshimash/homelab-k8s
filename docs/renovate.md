# Renovate - Automated Dependency Updates

This document describes the Renovate configuration and operational procedures for the homelab-k8s repository.

## Overview

[Renovate](https://github.com/renovatebot/renovate) is a dependency update tool that automatically creates pull requests when new versions of dependencies are available.

## Pinning Policy

Every version this repository controls is pinned in Git, and every change to a
pinned version arrives as a Renovate PR that a human reviews before merge. Two
properties follow from that, and both must hold:

1. **No silent updates.** Nothing changes on the cluster without a reviewed commit.
2. **Reproducibility.** Re-applying the manifests reproduces the same state.

Concretely:

| Kind of dependency | How it is pinned |
|--------------------|------------------|
| Helm chart | `spec.chart.spec.version` — an exact version, never omitted |
| Container image | `repository:tag@sha256:...` — tag *and* digest |
| Talos / Kubernetes | exact `vX.Y.Z` in `infra/talos/talconfig.yaml` |
| GitHub Action | tag + commit SHA (`helpers:pinGitHubActionDigests`) |

Omitting `spec.chart.spec.version` makes a HelmRelease follow whatever the Helm
repository serves, *and* makes the chart invisible to Renovate — the flux manager
only reports a dependency when a version is present. A floating image tag
(`:latest`, `redis:7-alpine`) behaves the same way at the container-runtime level.
Neither is acceptable in this repository.

## What Renovate Manages

### Automatically Tracked

| Type | Location | Manager |
|------|----------|---------|
| Helm chart versions | `k8s/infrastructure/**`, `k8s/apps/**`, `k8s/configs/**` | flux |
| Images in HelmRelease `values` | same paths | flux |
| Images in plain manifests | same paths, excluding `**/helmrelease.yaml` | kubernetes |
| Talos Linux | `infra/talos/talconfig.yaml` | regex customManager (`github-releases`) |
| Kubernetes | `infra/talos/talconfig.yaml` | regex customManager (`github-releases`) |
| GitHub Actions | `.github/workflows/*.yaml` | github-actions |

The `kubernetes` manager ships with an **empty** `managerFilePatterns` by design —
Renovate cannot guess which YAML files in a repository are manifests, so it parses
none unless told. Without the explicit `kubernetes` block in `renovate.json5`, no
`image:` reference in the app Deployments is tracked at all.

The two image managers must not overlap. The `flux` manager already extracts images
from a HelmRelease's `spec.values` (it reuses the `helm-values` extractor there),
which is how the runner image in `k8s/configs/arc-runners/helmrelease.yaml` is
covered. The `kubernetes` manager matches on any file containing both `apiVersion:`
and `kind:`, so it would read those same HelmRelease files and report the identical
image a second time — two managers, two groups, two PRs editing one line. A
`packageRules` entry therefore disables the `kubernetes` manager for
`**/helmrelease.yaml`. Add a new HelmRelease with images in its `values` and it is
covered automatically; add a plain Deployment and the `kubernetes` manager takes it.

Talos OS and Kubernetes produce Renovate PRs, but those PRs **do not apply
themselves** — merging updates Git only. See
[talos-operations.md — Renovate upgrade flow](talos-operations.md#renovate-upgrade-flow)
for the `talosctl` procedure that must follow the merge.

### Not Tracked (Manual Upgrade Required)

| Component | Location | Reason |
|-----------|----------|--------|
| Flux CD | `k8s/flux/flux-system/gotk-components.yaml` | Auto-generated by the Flux CLI; in `ignorePaths` |
| Immich sub-component images | chart defaults | Supplied by the pinned `immich` chart, not by our manifests |

## Configuration

The Renovate configuration is stored in `renovate.json5` at the repository root.

### Key Settings

| Setting | Value | Description |
|---------|-------|-------------|
| `prConcurrentLimit` | 10 | Maximum concurrent open PRs |
| `separateMajorMinor` | true | Separate PRs for major version updates |
| `automerge` | false | All PRs require manual review |
| `pinDigests` | true | Container images are pinned to an immutable digest |
| `minimumReleaseAge` | 3 days | A release must age before it is proposed |
| `schedule` | after 6pm on friday | Routine updates land off the working week |
| `labels` | `dependencies`, `renovate` | Labels applied to PRs |

Helm chart updates are grouped into a single `Helm charts` PR and container image
updates into a single `container images` PR, so the weekly batch stays reviewable.
The image group matches on **datasource** (`docker`) rather than on manager, so an
image found by the `flux` manager inside a HelmRelease lands in the image PR rather
than the chart PR. `separateMajorMinor` still splits major bumps out of those groups.

**Cilium is deliberately excluded from the chart group** and always gets its own
PR (`groupName: null` in a `packageRules` entry after the group rule; the option
defaults to null and grouping only applies when it is non-null, so a later null
drops the package back out). Two reasons, both learned from the
[2026-05-04 incident](incidents/2026-05-04-talos-1.13-cilium-1.19-tailscale.md):

- **Failure isolation.** Cilium is the CNI on a single node, so a regression
  takes the whole datapath down. Bundled with unrelated chart bumps, a
  post-merge failure cannot be attributed to one change.
- **The revert path is different.** Every other chart here rolls back with a
  revert PR that Flux reconciles. If a Cilium regression breaks pod egress,
  Flux cannot fetch the chart that would undo it — the GitOps deadlock. Recovery
  is an imperative `helm rollback` followed by a matching commit, which is a
  decision a human should be making deliberately, not one discovered mid-batch.

Before merging a Cilium bump, cross-check the target Kubernetes version against
the [Cilium Kubernetes compatibility list](https://docs.cilium.io/en/stable/network/kubernetes/requirements/)
for that release — the same matrix the
[Talos/Kubernetes PR review criteria](talos-operations.md#pr-review-criteria)
require for `kubernetesVersion` bumps. The two versions move together and must
not land in the same window.

### Excluded Paths

The following paths are excluded from Renovate scanning:

- `**/*.sops.yaml` - SOPS encrypted secrets
- `.sops.yaml` - SOPS configuration
- `k8s/flux/flux-system/gotk-components.yaml` - Flux auto-generated

## Workflow

### When a New Version is Available

1. Renovate detects the new version (within 24 hours)
2. A PR is automatically created with:
   - Version change details
   - Release notes link
   - `dependencies` and `renovate` labels
3. Review the PR and test if needed
4. Merge the PR
5. Flux automatically applies the change to the cluster

### Reviewing PRs

Before merging a Renovate PR:

1. Check the release notes for breaking changes
2. For major version updates, verify compatibility
3. Consider testing in a staging environment for critical components

## Manual Upgrade Procedures

### Talos Linux Upgrade

Talos and Kubernetes versions are defined in `infra/talos/talconfig.yaml`:

```yaml
talosVersion: v1.13.9
kubernetesVersion: v1.36.2
```

Renovate proposes the version bump as a PR; merging it changes Git only. The apply
procedure, health-check gate, and rollback strategy live in
[talos-operations.md — Renovate upgrade flow](talos-operations.md#renovate-upgrade-flow)
and must be followed manually after the merge.

### Flux CD Upgrade

Flux components are in `k8s/flux/flux-system/gotk-components.yaml`:

1. Check [Flux Release Notes](https://github.com/fluxcd/flux2/releases)
2. Run: `flux install --export > k8s/flux/flux-system/gotk-components.yaml`
3. Commit and push changes
4. Flux will self-upgrade

## Troubleshooting

### PRs Not Being Created

1. Check the [Renovate Dashboard](https://developer.mend.io/github/aoshimash/homelab-k8s) for status
2. Verify `renovate.json5` syntax is valid
3. Check if the component is in `ignorePaths`

### Too Many PRs

Reduce `prConcurrentLimit` in `renovate.json5` or close stale PRs.

### Dependency Not Detected

Check the "Detected Dependencies" section of the
[Dependency Dashboard issue](https://github.com/aoshimash/homelab-k8s/issues/120):
a file listed with no entries under it is being parsed but yields nothing, while a
file missing from the list entirely is not being parsed at all.

Then verify the file path matches the `managerFilePatterns` for the relevant manager
in `renovate.json5`. Two things bite here:

- `managerFilePatterns` entries are treated as **globs** unless wrapped in slashes.
  A regex must be written as `"/k8s/apps/.+\\.yaml$/"`, not `"k8s/apps/.+\\.yaml$"`.
  (`fileMatch` was the regex-only predecessor and is deprecated.)
- The flux manager reports a chart only when `spec.chart.spec.version` is set. An
  unpinned HelmRelease shows up as an empty entry on the dashboard.
